# 驱动模块产品设计

公共引用：[驱动私有DriverContext](linux/context.md)、[模块唯一职责](../architecture.md)。驱动和底层上下文分别维护，本页不复制结构。

驱动以LSM为核心，服务于AS的进程、文件、网络规则防护。核心目标是：在受保护效果发生前决定允许／阻止；需要人工选择时保留原操作，决定后继续或拒绝。参考实现与适用边界见[调研](references.md)，模块分工见[架构](architecture.md)，数据与等待契约见[技术细节](technical.md)。

## 技术选择与复杂度

部署要求是**保留用户现有发行版内核，通过安装包交付**。不采用需要编入新内核的自有内建LSM，也不要求安装TOMOYO或更换发行版安全模块。

驱动主线固定为**现有BPF-LSM入口＋一个可加载原生支撑模块＋独立的Rust底层**。BPF-LSM提供hook入口；驱动模块负责快速裁决、事件分流和原请求保管／等待／答复。内核规则表示的具体布置在实现前明确，不复制用户态可编辑规则源，也不承担进程树或协议解析。可睡眠入口通过正式kfunc调用原生等待，不用忙循环。

复用成熟加载／内核等待机制；AppArmor、TOMOYO作为可核对的实现参考，不成为额外必装的执法栈。其他技术只用于已明确且无法由主线满足的缺口，共用同一规则与问询流程，不自动降级或静默缩小条件。

产品安装包目标面向 Linux x86_64 与 aarch64。BPF 对象随包交付，原生模块由 DKMS 针对目标内核的匹配头文件和 BTF 构建。升级到新内核时沿用目标内核自己的构建输入。正式 deb/rpm 与安装升级链归 [AS 整体分发](../roadmap.md#as-整体分发)。用户已有的其他 LSM 继续生效，AS 允许只代表本模块的决定。

安装条件包括目标内核已提供BPF-LSM／BTF、所需hook与kfunc能力，以及可满足的模块加载和签名策略。缺失时明确报告不支持及原因，不要求用户换内核或把观察当保护。“不换内核”不等于所有机器都免重启：启用未启用的BPF-LSM或登记模块信任证书涉及启动流程时，安装器必须明确说明，不自动重启或关闭安全策略。

## 必须承载的核心需求

- **进程控制**：程序执行的允许／拒绝／问询；原进程和父进程身份；创建、执行、退出事实；按实际接口扩展进程间访问。fork／clone与exec分别定义，不把同一PID执行新程序说成创建新进程。
- **文件控制**：访问、写入、删除、重命名等按具体操作选取执行前检查点。只阻止打开不宣称控制已打开FD的后续写入；文件映射与异步I/O另核其实际入口。
- **网络控制**：连接及发送按真实socket／目标匹配；IPv4／IPv6和不同传输方式明确列能力。允许连接不自动永久允许该进程的一切流量。
- **容器范围**：所有受保护对象包含宿主机和容器；指定容器按所选实例，重建后不继承。同名、PID复用或cgroup编号复用都不能继承授权。
- **动作**：仅允许；仅阻止；阻止并终止原进程；阻止并终止原进程及原父进程。先拒绝原操作，再执行已授权终止范围，分别报告拒绝与终止的实际结果。
- **管理与自我保护**：初始化驱动及通信鉴权；规则更新收口到规则模块；功能开关实际改变执法；关闭、配置重载和驱动升级有真实结果。维护入口不能被普通Allow规则授予权限。
- **日志**：规则log字段决定是否记录；驱动产生结构化事实，消息线程交日志模块写入。日志失败不反转裁决，普通日志不主动推送给界面。

进程树必需的创建成功、exec成功和退出通知属于基础事实，不依赖是否命中防护规则、用户是否选择记录日志或前端是否在线；具体hook见[生命周期契约](linux/hooks.md#进程树必需的生命周期hook)。创建前允许不代表创建成功，单个线程退出也不代表进程结束。这些通知不产生新的阻止／问询能力。

这些是覆盖目标，不是已实现能力清单。某个核心操作缺少安全等待点时，该需求仍需解决，不能把问询悄悄换成直接允许／拒绝、事后处置或“仅观察”后宣布交付。规则不能表达当前执行点无法履行的动作。

## 普通文件模块范围

普通文件模块覆盖 Open、CreateFile、CreateDirectory、Unlink、RemoveDirectory、Rename、TruncatePath、TruncateOpenFile 和 MapSharedWritable，源码已在真实权限检查处接入原规则的Allow／Deny／ToUser；真实加载／保护效果由当前产物验收另行确认，不能只凭删除／改名的自保hook存在宣称已生效。操作和字段保持用户已有的文件规则池、编号与显式生效位置，不增加另一文件池或隐藏优先级。

截断问询保护已有文件免于缩短或清空。文件对象截断单独覆盖已持有 FD 和带截断标记的打开。共享可写映射问询保护通过映射回写修改文件的路径，规则在取得映射权限时裁决一次。AppArmor 同样区分路径截断、文件对象截断、映射和权限变更，并按共享映射实际回写语义检查写权限。它的内核裁决可作为能力参照，AS 的人工等待以本机实际 hook 验证为准。[AppArmor 截断](https://github.com/torvalds/linux/blob/v7.0/security/apparmor/lsm.c#L323-L329) · [AppArmor 映射](https://github.com/torvalds/linux/blob/v7.0/security/apparmor/lsm.c#L516-L547)

CreateFile 覆盖同次原路径可核实的具名普通文件创建，使用实际权限检查做 Allow、Deny 或 Ask。普通文件写入按打开和关闭处理。现有 Open 规则匹配写权限时，每次命中的原打开只问一次，已打开 FD 后续的 `write()` 不逐次问询。Allow 表示本次检查允许继续，实际文件效果独立确认。

写关闭属于事后审计。Linux 的通知由底层安全日志模块接收，范围由配置明确选择。文件落地检查、病毒扫描和哈希更新的接口仍待各自业务明确。[写关闭审计契约](../backend/security-log/technical.md#写关闭审计)

已有共享映射的写权限升级指进程先以只读方式共享映射文件，随后调用 `mprotect` 给同一段内存增加写权限。此调用无需再次打开文件，成功后进程可以通过内存写入改变文件内容。当前阶段只保留这次权限授予的自保检查。[驱动语义](linux/hooks.md#已有共享映射增加写权限) · [Linux mprotect](https://man7.org/linux/man-pages/man2/mprotect.2.html)

系统自保先拒绝不具修改权限的操作；权限通过不直接跳过普通规则。正常AS维护由同源规则数据直接Allow，避免自身等自己答复；根内目标的冷启动Open允许不能扩成外部修改权。双路径、真实模式和rename flag供用户理解原操作，其唯一字段定义见[事件契约](../contracts/events.md#普通文件gate字段与操作来源)，本轮不扩flags／mode匹配语言。

## 人工等待行为

驱动规则优先，其后是用户态记住、快速、询问规则。同类别同阶段内按组号、规则号首条命中，Allow／Deny／ToUser混合排列；不引入隐藏的阻止优先或允许优先。

ToUser表示原操作保持受控并进入用户态，不是LSM返回0。主模块一次处理一个活动人工问询，其他原请求有界排队；其他进程／容器的快速裁决继续。源有效期、规则超时、任务退出和取消仍有效，不承诺无限盲等。

无交互渠道时直接规则正常工作，不进入慢查询或询问池，不产生询问规则命中／日志；在途问询失去全部渠道立即采用原规则超时动作。驱动控制连接断开、内核容量不足或原请求失效是独立的故障，不能按“前端不在线”处理成允许。

AS允许仅代表本检查不拒绝；其他LSM、系统权限或实际I/O仍可能失败。界面不得把放行回执显示成操作已成功，也不得把已发送终止信号显示成进程已退出。

## 流量能力边界

LLM聊天、MCP、幻影key解析与必要替换属于独立流量能力；驱动只保管真实来源及执行对象，主模块只组合接口。传输、明文、分帧、替换和原生绑定见[联合设计](../backend/flow/design.md)。受控TLS入口、Flow协议采集和凭证注入已有对应实现；这不证明被动TLS或管道消息控制已接通。MCP管道控制仍暂缓，受管启动／接管pipe不作为通用监控前提；观察不冒充原操作控制或可写返回权。

仅迭代AS自身实现以减少额外处理，不修改或承诺加速Agent。网络I/O等待自然结果、真实错误、对端结束或显式取消；用户HIPS规则的原期限与超时动作单独保留。当前候选先完成已授权的完整实际工作流，再按原件分别报告结果；调研、源码、编译和可选验证不代替实跑，也不另设字段齐全、零丢样或精确归因门槛。

## 驱动与底层通信

初始化由主模块调用各模块初始化函数，并通过模块公开接口完成驱动初始化；规则编译不搬到主模块，配置仍是配置模块的一份只读快照。配置、驱动规则和实际状态使用同一条本机双向连接，跨系统业务接口保持相同含义。产品边界见[通信设计](../contracts/driver-communication/design.md)，平台选择和字段见[通信技术契约](../contracts/driver-communication/technical.md)。

## 内部职责拆分的目的

驱动内部按已有职责分为规则匹配、通讯、消息、配置，以及hook接入和原操作保管。这里的“子类”表示内聚实现单元，具体组合见[架构](architecture.md#内部子类与组合)，数据引用见[驱动内部文档入口](technical.md#唯一入口与子类文档)。不因拆分而增加产品能力、驱动数量或业务线程。

- 规则匹配按进程／文件／网络各走自己的驱动池，保留既定编号顺序和动作语义。
- 通讯处理真实连接与字节收发；消息处理当前驱动协议的请求、答复和事件。用户看到的问询、IM和配置管理入口仍属于主模块消息封装。
- 驱动配置只使用底层下发并实际采用的持久投影，维护非持久开关；读取、写入AS配置文件仍由底层配置模块完成。
- hook接入和原操作保管保证同一个执行点、原对象、期限及结果不因内部转交而丢失。内核DriverCore统一驱动实际状态，底层适配管理用户态加载与连接资源；二者不新增另一套生命周期服务。

子类不能扩大规则字段或把未知能力声明为可用。文件删除、完整自保、终止分项结果和流量替换仍按所属契约逐项明确；没有因为新增类名就完成这些能力。

驱动与底层是两个大模块，驱动只发送约定事件并在需要时保管原操作等待；底层负责其文件、编译、调度和人工渠道。上下文不复用，具体[边界](architecture.md#两个大模块的边界)同时约束文档与后续代码。

## 指定进程工具

底层可通过同一已鉴权驱动连接，指定真实宿主PID对应的进程实例发送SIGKILL。实例身份不符拒绝，不猜测替代目标；明确区分信号已接受和真实退出，不自动包含父进程。无状态工具边界及系统保护对象见[DriverTools](linux/tools.md)。规则的None／Actor／ActorAndParent已在原操作收尾复用此工具实现；真实结果分别显示阻止与每项信号接纳／失败，不从发送推定退出。
